RAG em base fiscal: por que o chunking padrão não serve e como corrigi

Rhuan Freire · Julho 2025 · 10 min de leitura

Documentos fiscais têm estrutura estranha — seções numeradas, remissões entre artigos, siglas sem contexto. O modelo padrão de RAG falha miseravelmente aqui. Essa é a história de como descobri isso e como resolvi.

O contexto do projeto

O cliente tinha uma base de ~12.000 documentos fiscais: instruções normativas, pareceres, regulamentos internos e respostas a consultas tributárias. O time jurídico-fiscal passava horas fazendo buscas manuais em PDF para responder perguntas que, no fundo, tinham resposta em algum lugar da base.

A proposta era direta: sistema de busca em linguagem natural que encontre o trecho relevante, cite a fonte e explique com contexto suficiente para quem vai usar na prática. Nada de chatbot genérico — a resposta precisa ser auditável.

O problema com chunking fixo

A abordagem padrão de RAG divide o documento em chunks de tamanho fixo — digamos, 512 tokens com overlap de 50 tokens — e indexa cada chunk separadamente. Em textos narrativos como artigos de blog ou documentação técnica, isso funciona bem.

Em documentos fiscais, não funciona. O motivo principal é a remissão entre artigos:

Art. 23. Para fins do disposto no art. 14, §2º, inciso III, da
Instrução Normativa RFB nº 1.700/2017, considera-se...

Se você chunkar esse parágrafo isolado, ele não faz sentido sem o Art. 14 da IN 1.700/2017. O modelo vai gerar uma resposta tecnicamente fundamentada, porém errada por falta de contexto.

Chunking estrutural

A solução foi usar a própria estrutura do documento como guia de chunking. Documentos fiscais têm hierarquia bem definida: Capítulo → Seção → Artigo → Parágrafo → Inciso. Em vez de dividir por tamanho, dividi por unidade semântica natural.

Cada chunk virou um artigo completo (mesmo que longo), com metadados que incluem:

  • Identificador do documento fonte
  • Numeração do artigo dentro do documento
  • Lista de artigos referenciados no texto
  • Data de vigência do documento
  • Tipo do documento (IN, Parecer, Resolução)

A indexação das referências foi o ponto mais importante. Quando um artigo cita "art. 14, §2º da IN 1.700", essa referência fica explícita nos metadados. Na hora da busca, além do chunk mais relevante semanticamente, o sistema busca automaticamente os chunks referenciados e os inclui no contexto.

A resposta auditável

Num contexto fiscal, o usuário não pode confiar numa resposta que não cite a fonte exata. A solução foi estruturar o output do modelo com um campo obrigatório de citação:

{
  "resposta": "Com base no art. 23 da IN RFB 1.234/2024...",
  "citacoes": [
    {
      "documento": "IN RFB 1.234/2024",
      "artigo": "Art. 23",
      "trecho": "considera-se receita bruta o produto da venda...",
      "vigencia": "2024-01-01"
    }
  ],
  "confianca": 0.87,
  "observacao": "Verificar se houve alteração posterior à data de publicação"
}

O campo confianca não é gerado pelo modelo diretamente — é calculado com base no score de similaridade do chunk mais relevante encontrado. Se estiver abaixo de 0.7, o sistema avisa que a base pode não ter a informação necessária.

O que melhoraria

A extração da estrutura dos documentos dependeu de parsing manual com regex e heurísticas — funcionou para os documentos do cliente, mas não é generalizado. Hoje usaria um modelo de visão para extrair estrutura de PDFs mais complexos antes de indexar.

O outro ponto: a base fiscal muda. Documentos são revogados, artigos são alterados. O sistema atual não tem um mecanismo de invalidação automática — precisa de atualização manual quando há mudanças na legislação.

Em RAG para documentos críticos, a citação não é um diferencial. É o mínimo.
