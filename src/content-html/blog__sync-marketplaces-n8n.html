Sincronizando 3 marketplaces com n8n: o que aprendi sobre idempotência

Rhuan Freire · Junho 2025 · 7 min de leitura

Construir o fluxo de sync foi fácil. O que quase me matou foi descobrir que o mesmo pedido pode chegar 3 vezes em 200ms — e você não pode processar duas delas.

O problema de sincronização multi-canal

O cliente vendia no Mercado Livre, Shopee e seu próprio e-commerce. Cada venda numa plataforma precisava atualizar o estoque nas outras duas e registrar o pedido no ERP interno. Com volume baixo, ninguém percebe o problema. Com 200 pedidos por hora no pico, o problema aparece rápido: estoque negativo, pedidos duplicados, divergências que só aparecem no fechamento do dia.

O n8n foi escolhido porque o cliente já tinha familiaridade com a ferramenta e eu precisava de algo que o time de operações conseguisse acompanhar e modificar sem envolver engenharia a cada mudança.

O evento duplicado que quase virou pesadelo

Marketplaces enviam webhooks com retry automático. Se seu endpoint demorar mais de 5 segundos para responder, a plataforma reenvisa o mesmo evento. Se cair dentro de uma janela de retry, você pode receber o mesmo pedido 3, 4, 5 vezes.

O fluxo ingênuo processa cada evento que chega. O resultado em produção: pedidos duplicados no ERP, estoque que baixava duas vezes pelo mesmo pedido, alertas de estoque negativo que assustaram o time de operações.

A solução foi implementar uma tabela de idempotência simples no Postgres:

CREATE TABLE processed_events (
  event_id TEXT PRIMARY KEY,
  source TEXT NOT NULL,          -- 'mercadolivre' | 'shopee' | 'site'
  processed_at TIMESTAMPTZ DEFAULT NOW(),
  payload JSONB
);

Antes de processar qualquer evento, o fluxo n8n faz um INSERT ... ON CONFLICT DO NOTHING e verifica o resultado. Se a linha não foi inserida, o evento já foi processado antes — encerra o fluxo sem fazer nada.

O problema de ordem dos eventos

Idempotência resolve duplicatas, mas não resolve ordem. Num pico de tráfego, você pode receber:

  1. Evento: "pedido 123 confirmado" (às 14:32:00.100)
  2. Evento: "pedido 123 cancelado" (às 14:32:00.150)
  3. Evento: "pedido 123 confirmado" novamente por retry (às 14:32:00.200)

Com idempotência simples, o retry do evento confirmado seria ignorado — certo. Mas se o cancelamento chegar antes do primeiro evento confirmado, você confirma um pedido que deveria estar cancelado.

A solução foi adicionar event_timestamp ao payload de cada evento (o timestamp do evento na plataforma de origem, não o momento de recebimento) e só aplicar a mudança se o timestamp for mais recente que o último estado registrado para aquele pedido.

Monitoramento: o que o n8n não te dá

O n8n tem logs de execução, mas não tem uma visão consolidada de "quantos eventos processados nas últimas 2 horas" ou "qual o tempo médio de processamento por tipo de evento". Para isso, adicionei uma etapa de registro no Postgres ao final de cada fluxo bem-sucedido:

{
  "flow": "marketplace_sync",
  "source": "mercadolivre",
  "event_type": "order_created",
  "duration_ms": 342,
  "status": "success",
  "timestamp": "2025-06-15T14:32:00Z"
}

Com isso, um dashboard simples no Metabase deu ao time de operações visibilidade em tempo real — sem precisar abrir o n8n.

O que não escala nessa arquitetura

O Redis como lock distribuído para evitar race conditions funcionou no volume atual. Com 10x o volume, a fila de webhooks esperando o lock vai criar latência visível. A solução para esse caso seria migrar para uma fila de mensagens dedicada (SQS, Pub/Sub) e processar os eventos em paralelo com deduplicação por event_id.

Idempotência não é uma feature. É o que separa um sistema que funciona de um que às vezes funciona.
